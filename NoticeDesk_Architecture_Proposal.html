NoticeDesk Internal — Architecture Proposal

Proposed Hybrid Architecture
Gemini Flash Classifier as Layer 2

Solving the Vocabulary Mismatch Problem in Notice Routing
Prepared by: Sonia (Intern)
Date: September 2026
Purpose: Mentor Review — Architecture Discussion

1. Background & Problem Statement

NoticeDesk's drafting engine uses a 3-tier strategy to generate legal reply drafts for incoming GST notices. The decision of which tier to use is made by a keyword-based scoring system.

StrategyWhen UsedCost / NoticeSpeed
Fast-TrackExact keyword match (score ≥ 90%)$0.00< 150 ms
HybridPartial keyword match (score 70–89%)~$0.07~4 sec
Novel LLMNo keyword match (score < 70%)~$0.12~7 sec

The Core Problem

Problem: The entire routing decision sits on keyword matching only. A GST notice may describe a well-known legal issue using entirely different words or phrasing than what the keyword scanner expects — causing the system to miss a perfectly good existing draft template and fall through to a full, expensive Claude call.

This is called the Vocabulary Mismatch Problem. Here are real examples:

What corpus template coversHow incoming notice might phrase it
"wrongful availment of Input Tax Credit" "ITC claimed without valid invoices" ← keyword match fails
"tax evasion under Section 74" "willful misrepresentation of taxable turnover" ← keyword match fails
"mismatch in GSTR-2A vs GSTR-3B" "discrepancy between purchase records and filed returns" ← keyword match fails

All three pairs describe the exact same legal issue. But keyword matching fails on the right column — routing these to Novel LLM and paying $0.12 for a Claude call when we already had the draft ready.

2. Proposed Solution

Key idea: Insert a lightweight classification step using Gemini Flash between the keyword scorer and the full Claude drafting call. Flash is used only to classify the notice type — not to draft the reply. This costs ~$0.001 and takes ~1 second, but lets us do a smarter corpus search by meaning rather than exact words.

3. Proposed Architecture — Step by Step

1

Layer 1 — Keyword Scoring $0.00  |  <1 ms

Already built. Checks for exact form codes and section numbers (DRC-01, Section 73/74, Section 16(4), etc.) in the notice OCR and metadata.

If score ≥ 0.90 → FAST_TRACK immediately. Done.
If score < 0.90 → fall through to Layer 2.

2

Layer 2 — Gemini Flash Classifier ~$0.001  |  ~1 sec

New component: NoticeClassifierService.
Sends the first ~1500 characters of the notice OCR to Gemini Flash with a short structured prompt. Flash returns a JSON classification — NOT a legal draft:

{ "section_refs": ["73", "16(4)"], "issue_tags": ["itc_mismatch", "gstr2a_dispute"], "form_type": "scn", "confidence": 0.91 }

Cost: ~500 input tokens + ~50 output tokens ≈ $0.0003 per notice at Gemini Flash pricing.

3

Layer 3 — Corpus Tag Search $0.00  |  <1 ms

Enhancement to GstCorpusMatcherService (new matchByTags method).
Uses the section_refs and issue_tags from Flash to search the 301-pair corpus manifest for the closest matching draft template — by meaning and legal category, not by exact keyword presence.

4

Final Routing Decision

High corpus match (≥ 0.90) → FAST_TRACK — template fill, no Claude call needed.
Medium match (0.70–0.89) → HYBRID — template used as reference, Claude synthesizes.
Low / no match (< 0.70) → NOVEL_LLM — Claude generates from scratch, result cached.

4. Classifier Prompt (What Flash Is Asked)

This is the exact short prompt sent to Gemini Flash — purely for classification, not drafting:

You are a GST legal notice classifier. Read the notice below and return ONLY a JSON object with: - "section_refs": list of GST sections mentioned or implied (e.g. ["73", "74", "16(4)", "129"]) - "issue_tags": 1 to 3 tags from this fixed list ONLY: ["itc_mismatch", "tax_evasion", "gstr2a_dispute", "eway_bill_violation", "registration_cancellation", "export_refund", "reverse_charge", "audit_discrepancy"] - "form_type": one of: ["scn", "drc_01", "order_in_original", "apl_01", "asmt_10", "reg_17"] - "confidence": your confidence score between 0.0 and 1.0 Return ONLY valid JSON. No explanation. NOTICE TEXT: {first 1500 characters of OCR text}

Token cost estimate: ~500 input tokens + ~50 output tokens ≈ $0.0003 per classification.

5. Cost & Speed Comparison

ScenarioCurrent SystemProposed System
Keywords hit (exact match) $0.00, <1 ms $0.00, <1 ms ✅ No change
Keywords miss, but draft exists in corpus $0.12, ~7 sec ❌ $0.001, ~2 sec ✅
Truly novel notice (no corpus match) $0.12, ~7 sec $0.001 + $0.12, ~8.5 sec (minor overhead)
Savings estimate: If even 30% of notices that currently fall through keyword matching actually have a corpus match, the classifier layer saves ~$0.12 per notice on those cases at a cost of only ~$0.001 for the Flash call — a 99% cost reduction per rescued notice. At 100 notices/day, this saves approximately $3–$4/day while improving draft quality.

7. Open Questions for Mentor Review

  1. Should the issue_tags vocabulary be expanded beyond the current 8 tags? Real-world GST notices may cover a wider taxonomy of disputes.
  2. Should the classifier's confidence score act as a hard gate? If it returns confidence < 0.7, should we skip corpus tag search and go straight to Novel LLM?
  3. Is the extra ~1–2 seconds latency from the classifier call acceptable in the partner-facing UI?
  4. Fallback behaviour: if the classifier API is unavailable (rate limit / outage), should we fall back gracefully to the current keyword-only path or block the draft?
  5. Corpus tagging strategy: should we retroactively tag all 301 corpus pairs with issue_tags manually, or let the classifier auto-tag them during a one-time indexing run?
  6. Which LLM should we use for the classifier? (See Section 8 below for full comparison.)

8. LLM Options for the Classifier Layer

The classifier only needs to read ~1,500 characters of notice text and return a small JSON object (~50 tokens). This is a very simple task — the model choice is almost entirely a cost, latency, and vendor-risk decision. Below is a full comparison of available options, including which are already wired into our codebase.

What we need from the classifier model:
~500 input tokens (notice OCR excerpt) + ~50 output tokens (structured JSON) = ~550 tokens total per call. The model must reliably return valid JSON. No legal reasoning needed.

Per-Model Verdict

Already wired into our codebase via GeminiLlmProvider.java. Same Google ecosystem we already use. Excellent at structured JSON output. No new API key or dependency needed. Recommended choice.
Zero new dependencies · Lowest operational risk
🥇 Equal Pick GPT-4o mini ~$0.0001 / notice
Same cost as Gemini Flash. Already wired via OpenAiLlmProvider.java. Industry-standard JSON mode support — extremely reliable at returning valid structured output. Good as a fallback if Gemini is unavailable.
Good fallback · OpenAI-compatible endpoint
🥈 Viable Claude Haiku 3.5 ~$0.0006 / notice
Already wired via AnthropicLlmProvider.java. Same vendor as our drafting model (Claude Sonnet). However, costs 4–6× more than Gemini Flash or GPT-4o mini for an identical classification task. Not recommended unless we have strong vendor-consolidation reasons.
Same vendor as drafter · Higher cost for same output
🚀 Explore Later Llama 3.1 8B via Groq ~$0.00003 / notice
10× cheaper than Gemini Flash. Extremely fast (~300 ms). Open-source model. Groq uses an OpenAI-compatible API, so OpenAiLlmProvider.java can point to it with just a baseUrl change. Main risk: smaller models need more careful prompt engineering to reliably return valid JSON every time.
New API key needed · Worth evaluating in Phase 2
❌ Do Not Use Claude Sonnet 4 ~$0.002 / notice
This is our full drafting model. Using it just to classify a notice type is like hiring a senior lawyer to read the notice number off the envelope. 20× more expensive than Gemini Flash for the same classification output, with no quality benefit.
Reserve for drafting only · Not suitable for classification
